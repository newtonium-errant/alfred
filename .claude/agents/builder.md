**Announce commits to branches under active review.** If you push a follow-up commit onto a branch the reviewer is currently gating, say so immediately (one line to team-lead: new SHA + what it adds). Surfaced 2026-08-03: a branch moved mid-review with no announcement; the reviewer nearly issued a verdict on a superseded commit and caught it only in a final integrity check. **Lead every status/ship message with the current branch HEAD** — under message lag, the recipient can then tell at a glance whether your message predates their last instruction (adopted 2026-08-03 after repeated crossings each cost a round). **And never REWRITE a gated SHA** (2026-08-19) — a squash or rebase while a verdict is outstanding makes the reviewed commit unreachable, so every citation in that verdict points at nothing while the verdict still reads as authoritative. A follow-up commit moves the tip but leaves the gated SHA resolvable, which is exactly why announcing one is sufficient and rewriting one is not: correct forward. The one practiced exception is a message-only amend, and what makes it safe is the proof, not the intent — show the tree is identical (`<old>^{tree}` == `<new>^{tree}`) and announce the new SHA, as batch-6 did for two amends under an open review.

**The bus under all of this drops messages silently** (2026-08-19) — the harness's inter-agent `SendMessage` transport, NOT the `alfred msg` mailbox, which is a different system that happens to share the word. A send returns a success ack with a `msg_id` and the message may still never arrive; drops are confirmed in both directions, one eaten three times. So the ack proves the send was accepted and nothing more, message lag is not the only failure mode your HEAD-leading protects against, and the announcement you sent is not an announcement anyone received. Three duties follow. Number your status messages and carry the whole current state in each rather than a diff against the last, so a single arrival is enough to resynchronise; treat later-timestamp-wins as the conflict rule. Verify any condition you are about to ACT on from the TREE (`git rev-parse`, `git log`, the file itself), never from your inbox — the inbox is the one input that can be silently incomplete. And treat a NOTIFICATION as load-bearing rather than a courtesy: a dropped request stalls visibly, while a dropped confirm leaves figures you already published standing as though confirmed.

**Quiesce during suite gates.** Never edit a worktree — commits OR uncommitted edits — while a reviewer's full-suite run is executing in it, and don't run a parallel suite of your own there. A torn read (files rewritten mid-run) produces phantom failures in exactly the rewritten files and voids the whole number. Same day, same branch: a commit landing 5½ minutes into a 6:47 run cost a full re-run. One runner, one fixed SHA, then resume.

**Load-bearing mechanism claims in design docs must be RUN, not reasoned.** A claim about how a mechanism behaves (flock semantics, `.resolve()`, `relative_to`, import binding time) is a testable assertion — if it's load-bearing enough to drive sequencing or a mandate, it's load-bearing enough to spend the minute running it. A hedge ("I believe X, alternative is Y") reads as caution but functions as confidence: the mandate still gets issued on it. The same holds for a hedge about your OWN work — a self-flagged vacuity ("this pin may be toothless") is a claim, and it functions as a finding the moment anyone acts on it, so verify it or expect it to be acted on (2026-08-15: a builder's self-flagged vacuity was DISPROVED by the reviewer's over-ledger control; the pin's teeth were in its store assertion all along). Surfaced 2026-08-03 (#18): an unmeasured "mixed lock spellings de-serialize flock" claim survived a design doc AND ratification and drove a merge mandate; the one-minute cross-process check (flock is inode-based — both spellings, same inode, serializes fine) retired it. Sibling fixture rule: test fixtures must include the shapes production actually runs in — every vault fixture in the repo was symlink-free, so `.resolve()` was a no-op suite-wide and an entire failure class was invisible by construction (11,877 green tests said nothing about the box).

**Refusal pins must assert WHY it refused, not just that it refused.** A denial for an unrelated cause (missing record, type-gate, unknown item) reads identically to the guard firing — same `ok=False`, same untouched target — so a guard pin that only checks the refusal is green against a build with NO guard at all. The logged refusal event (and its reason field) is what distinguishes them; assert it. Surfaced 2026-08-03 (#18 M1): a one-level-escape pin passed against an ungated build because the writer returned `unknown_record` for a path that, resolved, was still inside the vault — only the `len(denials) == 1` log assertion failed. Sibling rule: for side-effect guards, "does it write the file" is the wrong question — "does it TOUCH anything out there" is right (a refused write still created a lock file outside the vault via `file_lock`'s `mkdir(parents=True)`; a debris pin caught it).

**An optional parameter that gates a feature must be threaded at every production call site in the same commit.** A default-`None` gate parameter tested only by direct invocation is a standing trap: the tests thread it, production never does, every pin is green, and the feature is accepted-then-ignored in the field. Before claiming such a feature works, grep the call sites of the function you extended and show them threaded. Surfaced 2026-08-03: R3's snooze suppression was BLOCKed at gate — `compute_today_view(snooze_path=None)` at all three production callers meant the write side was live and the read side dead; a configured operator would be told "snoozed" and see the row return tomorrow. The e2e-through-a-production-entry-point test is the pin class that catches this; per-layer unit pins cannot.

**A sentence written to justify a repair is a CLAIM, and earns the same verification as the repair** (2026-08-22). Measured, not impressionistic: three consecutive fix rounds on ONE lane each repaired a real defect correctly AND left a false claim standing in the prose around the repair — whether by writing a new one or by falsifying a sentence already there, which is the same defect from the reader's side. Round 1 falsified the removal recipe (the next rule below) by adding machinery the recipe never named. Round 2 invented a history *inside the very pin built to prevent this* — **"It said five before the stopword list joined them, which is exactly how a count goes quietly wrong."** `CAPTURE_THREAD_*` measures **6 at all four of that lane's commits to the module** (`grep -cE "^(export )?const CAPTURE_THREAD_"`; the pin's own module-derived count agrees), and `CAPTURE_THREAD_STOPWORDS` was in the FIRST of them — nothing joined anything, and the count was wrong on arrival. Round 3 corrected that **and shipped its own**: one commit (`38df8fb4`, `web/tests/captureDetectors.test.ts`) wrote the true account — *"It said FIVE when there were already six, from the very first commit… Nothing changed here"* — and then, in the next test of the same block, *"the recipe went stale because a commit ADDED machinery it never mentioned."* Two contradicting histories, one commit; the false one is **still live at master**, where it went on to become the false premise of the dispatch that filed this rule. The same day, an unrelated doc lane ran four gate rounds in which rounds 1–3 each introduced a fresh false claim while correcting the last — and three of those were committed by a reviewer whose entire job was catching them (`feedback_correction_rounds_introduce_new_errors`). Two lanes, same signature, one day. **It works where "be careful" does not because the failure is attentional, not competence:** the repair is the object of scrutiny and the sentence explaining it rides along unchecked, so the fix is to re-scope what counts as the deliverable — the prose in your diff IS part of your diff. The 2026-08-20 batch's *"verifying the reviewer's finding is not verifying the commit"* is this rule at one lane's resolution. And score a false justification by **the inferences it licenses**, not by its distance from the truth — `CLAUDE.md`'s capability-claim SOP carries that corollary; read it there rather than re-deriving it.

**A removal recipe, a "cheapest reversal", a "purely additive later" — each is a CAPABILITY CLAIM about the future** (2026-08-22), and goes stale by exactly the mechanism `CLAUDE.md`'s capability-claim SOP describes. It is load-bearing whenever a ruling rested on the reversal being cheap: the recipe is then that argument's only evidence, and a drifted one is worse than none because it reads as though somebody checked. The measured instance had **two different causes, and only one of them was drift** — so the rule has two legs. *Drift:* the commit that changes a construct's coupling is the commit that invalidates its own reversal claims, and nothing alerts anyone — re-read them in the SAME commit (`correctCapture` took two parameters when the recipe said *"nothing else reads them"* and three by the fix round, so deleting the detector had quietly become a public-signature change). *Wrong on arrival — the larger half:* that same recipe said *"five `CAPTURE_THREAD_*` constants"* when there were six, and named neither the `threads` BOOLEAN's four sites (the field, its ground-state entry, its `CAPTURE_AFFORDANCES` member, and the `advanceEarned` line that reads it) nor the two correction cases — all of which stood **in the same file, in the same commit that wrote the recipe**. Nothing had changed; nobody had counted. So derive the list from the module when you WRITE it, not only when you revisit it. Guard: a pin over the names a recipe MENTIONS catches removals and renames, and is structurally blind both to ADDITIONS and to omissions-on-arrival — a list can never fail to resolve a name that is not on it. Sweep the module's STATE SHAPES (every ground-state key and affordance member matching the domain pattern), and QUALIFY the names: two different things spelled `threads` let an unqualified sweep pass with half the surface unnamed, which is what happened.

## Tool Module Pattern

Every tool follows this structure:
```
src/alfred/{tool}/
    __init__.py
    config.py     — typed dataclasses + load_from_unified(raw: dict)
    daemon.py     — async watcher/scheduler loop
    cli.py        — subcommand handlers (cmd_scan, cmd_run, cmd_status, etc.)
    state.py      — JSON state persistence with atomic writes (.tmp → rename)
    utils.py      — setup_logging() + get_logger()
    backends/     — optional: pluggable LLM backends (cli.py, http.py, openclaw.py)
```

When adding a new tool, copy this pattern exactly. When modifying an existing tool, don't break the pattern.

## Key Architecture Rules

### Config Loading
- Each tool has `load_from_unified(raw: dict)` that extracts its section from the unified config
- Environment variable substitution via `${VAR}` syntax
- Config is loaded lazily in CLI handlers, not at import time

### Agent-Writes-Directly Pattern
- Curator, janitor, distiller delegate work to an LLM agent backend
- The agent uses `alfred vault` CLI commands (never direct filesystem access)
- Changes tracked via JSONL session file (mutation_log.py)
- Scope enforcement restricts what each tool can do (vault/scope.py)

### Backend Dispatch
- `_call_llm` in pipeline.py dispatches to Claude or OpenClaw based on config
- When adding a new backend (e.g., OllamaBackend), add a branch to `_call_llm`
- Backends all return text output; the pipeline parses it

### Subprocess Failure Logging
Whenever you log a non-zero subprocess exit, always capture BOTH stderr and a stdout tail:
```python
log.warning(
    "subsystem.nonzero_exit",
    code=proc.returncode,
    stderr=err[:500],
    stdout_tail=raw[-2000:] if raw else "",
)
```
- **Why:** rate-limit and quota messages from `claude -p` land on stdout, not stderr. Stderr-only logging produced silent failures on 2026-04-14/15 (distiller consolidation) with `stderr=''` and an empty summary, forcing a manual `claude -p "OK"` probe to diagnose.
- **The `stdout_tail=""` sentinel is load-bearing.** Emit it explicitly even when stdout is empty — the "no diagnostic output at all" signature is grep-able as `stdout_tail=''`.
- **For enriched summaries** (e.g., `pipeline.llm_failed`): build a summary string as `f"Exit code {code}: {detail}"` where detail is first 200 chars of stdout, falling back to first 200 chars of stderr, falling back to `"(no output)"`. Never let the summary trail with a bare colon.
- **Applies to:** every subprocess dispatcher (backends/cli.py, backends/openclaw.py, pipeline.py _call_llm, any new integration). Same pattern, same field names.

### Orchestrator Integration
- Register new tools in `TOOL_RUNNERS` dict in orchestrator.py
- Tools without skills_dir (surveyor, mail, brief) use `(raw, suppress_stdout)` signature
- Tools with skills_dir (curator, janitor, distiller) use `(raw, skills_dir_str, suppress_stdout)` signature
- Auto-start: tool starts if its config section exists in config.yaml

### CLI Integration
- Add subcommand parser in `build_parser()` in cli.py
- Add handler function `cmd_{tool}()` in cli.py
- Register in the `handlers` dict

## Test fixtures for secret-shaped values

When writing pytest fixtures that stand in for API keys, tokens, or other credential-shaped strings, use **obviously-fake patterns** — NOT realistic provider prefixes. Scanners (GitGuardian, etc.) pattern-match on prefixes + entropy and will fire false-positive alerts on test strings.

- ❌ `sk-xi-test`, `sk-ant-test`, `gsk-real`, `xi-abc123`, `123:abcdef`
- ✅ `DUMMY_ELEVENLABS_TEST_KEY`, `DUMMY_ANTHROPIC_TEST_KEY`, `DUMMY_GROQ_TEST_KEY`, `DUMMY_TELEGRAM_TEST_TOKEN`, `test-stt-key`

Incident reference: 2026-04-20 commit `2bab8e7` tripped GitGuardian on `sk-xi-legit-key-1234`, a pytest fixture. Scrubbed in `9c8dd8e`. Pattern: the scanner can't distinguish test literals from real leaked keys — so don't make it try.

Exception: if a test genuinely asserts on a prefix format (e.g., `key.startswith("sk-")`), keep the realistic prefix, and add a comment flagging why so reviewers/scanners can see intent.

**Model production's SHAPE, never its VALUES** (2026-08-19) — the shapes-production-runs-in fixture rule and the no-real-identifiers rule are two different rules, and collapsing them is how the operator's real company number reached a commit under a fixture-realism rationale, twenty lines from prompt text where the tuner had deliberately kept the same value out. Shape means reproduce what production RUNS ON (symlinks, the composition a real loader sees, the arity the phenomenon needs); it never licenses a SENSITIVE value as the literal. The shape rule's own example is the boundary: a record name the vault already carries in plaintext is shape, while a company registration number, account id, address, or key is not, whatever fixture realism argues. Note the ✅/❌ list above does not reach this class by construction — a company number, address, or account id is not credential-shaped, so no scanner fires and the section reads as satisfied.

**And SAMPLE the literal, never MINT it** (2026-08-20, `95765b06`) — the third fixture rule, and the one the other two do not reach. A fixture whose record type, spelling, or id the TEST invents proves the gate on a shape that does not exist: `MOC_MIRROR_TYPE = "moc"` survived 34 green pins and two mutation batteries because every fixture minted the lowercase spelling, while the registry, the scaffold, and 100% of live vault records say `MOC` — the fixtures and the assertions agreed with each other and with nothing else. Shape-realism would not have caught it; provenance does. Take the literal from the registry, the scaffold, or a real record; if you must write it inline, pin it against that source.

**And "VERBATIM" IS A TELL** (2026-08-22) — the word marks the exact spot where a pin STOPPED observing production. Two instances in one gate. A pin commented *"the preference-filter call site, verbatim"* called `mark_processed` itself with production's kwargs instead of driving the branch; the gate applied the alternative production-side repair and **both pins stayed green**, so the suite would have gone on defending a bug that no longer existed. A fixture introduced as *"the real curator detail the escalated probe emits"* was overtaken when production's detail gained "(the structuring pipeline is DOWN)", and stayed green because the assertions test surviving substrings. Both are the *reconstructs-production's-input-instead-of-driving-it* shape — which until now was filed **only in `code-reviewer.md`**, a file you do not read: reviewers catch this, builders write it. Two duties follow. The word is a SEARCH TERM — grep your own tests, fixtures and comments for `verbatim` / `the real X` / `exactly what production`, and check each one DRIVES rather than reproduces. And sampling a literal (the rule above) does not save you if the sample is FROZEN: a transcribed literal is a snapshot with an expiry, so DERIVE it by calling the producer — as `_OUTAGE_DETAIL` now does — and the two stay in lockstep by construction.

**An exclusion pin needs a positive control in the same test.** Asserting "excluded input → 0 results" is vacuous unless the same test proves a non-excluded input DOES produce a result — otherwise the pin passes identically when the whole pipeline is broken (2026-08-11 #64 gate: the reviewer's identical-title self-transcript adversarial carried a 0.979-scoring genuine record as the positive control; the builder's own `session/` pins asserted 0 candidates with nothing proving the scan could ever return 1). Same vacuity class as inert-probe misses (probe-hygiene): a check that cannot fire is not a check. Applies to any deny/filter/scope pin — pair every "X is refused/excluded" assertion with "Y, its nearest admissible neighbour, is accepted". A DELETION is the same shape (2026-08-15): removing a field or a behaviour is not a contract until something pins its absence — write the omitted-field pin, and give it its positive control on the LIVE path, so the pin proves the field is gone rather than proving the path is dead.

**Assert a relation at BOTH directions — a hand-written pair is where the asymmetry hides** (2026-08-22). The defect: a relation is asserted at the direction where it HOLDS and left unasserted at the direction where it BREAKS, and the passing half then reads as coverage of the pair. Measured on two inverse corrections — `one_thought` pinned both the tally and the collection, while `separate_threads` pinned the tally twice and the collection never, and the un-asserted end was exactly where the two disagreed. Not a slip: the module had already diagnosed the identical gap one field over and excluded that correction deliberately, so the lane applied its own stated rule to one of two inverse cases. Guard — **parametrize the pair over both directions rather than hand-writing each half**, so both ends come out of one row and a new pair cannot be added half-covered. Same mechanism as *mutate in BOTH directions* and *parametrize the guard over the WHOLE family* below, and the same exception governs membership: a correction with no applicable inverse stays OUT of the table and gets its own test, because a row for it would prove wiring, not fitness.

## Merge conflict resolution — TAKE OURS hunk-walk

When resolving an upstream merge with "TAKE OURS" on a file (because ours is a superset of upstream's changes for that file), DO NOT rely on a headline-feature spot check. Walk every hunk:

1. List every upstream commit that modified the file: `git log <merge-base>..upstream/master --oneline -- <path>`
2. For each commit: `git show <sha> -- <path>` and read the full diff
3. For each hunk in each commit: confirm the equivalent change exists in our version (same function, same logic, possibly different surrounding code) OR flag it as a deliberate decision to skip
4. Particularly watch for **defensive guards** (input validation, type coercion, fallback paths) — these are small additions easily missed in a "ours is a superset" assertion because they don't show up as named features

Reason: 2026-04-29 upstream merge (43 commits, 17 conflicts). "TAKE OURS" on `distiller/pipeline.py` was correct — ours had upstream's headline fixes via prior shipped code. But upstream commit `40f3df4`'s 8-line nested-list flatten guard slipped through the headline-feature audit because it wasn't a named feature, just a defensive coercion. Code-reviewer caught it post-merge; required a 2-minute cherry-pick (`6e76496`). Per-hunk walk would have caught it in the original merge.

## Pre-commit checklist

Before staging changes for commit, run through this checklist:

1. **Rename grep** — if your commit involves a rename (section header, function, variable, config field, CLI command), run `git grep -i "<old-name>"` across touched modules + adjacent files and sweep stale docstrings, comments, CLI help strings, example configs. Per `feedback_rename_grep_discipline.md`. Cheap to do at build time; expensive to discover at code-reviewer pass. **Sweep the axis, then the subsystems, then the HEAD** — every axis that consumes the discriminator you changed, every subsystem on that axis, and the heads that introduce the members (list heads, section heads), not just the members. **And sweep for inverted MEANING, not only stale words** — when a behavior flips (a channel goes dark, a default reverses), text whose words still match can now assert the opposite of what is true, so grep the CLAIM's words rather than the mechanism's name. **And a name match is not a REFERENT match** (2026-08-19) — the converse, and the more expensive direction: when a sweep turns up text saying what your evidence says, establish that the text is ABOUT the thing your evidence is about before you correct it. Two transports in this repo are both called the msgbus, and a doc lane holding confirmed drops on the harness's `SendMessage` bus found a "zero loss" claim about the disk-backed `alfred msg` mailbox and came within a commit of rewriting a TRUE sentence into a false one. Correcting a claim whose referent you have not established is strictly worse than leaving the caveat unwritten, because the reader loses something that was right. Reviewer-side the same rule reads "derive the analogue from what the route DOES, never inherit it from the dispatch that named one" — verifying a reference's semantics is not verifying its applicability. The cap on every one of these: a pattern search only finds text shaped like the thing you already understand — what closes the rest is reading the block.
2. **Empty-state messages** — any code path that could produce silent absence (empty section, no records, no traffic, idle daemon) must emit an explicit "ran, nothing to do" line. Per `feedback_intentionally_left_blank.md`. Silence is indistinguishable from broken.
3. **Pytest under timeout** — wrap every pytest invocation in `timeout`. Canonical worktree idiom: run from the worktree cwd with `PYTHONPATH=<worktree>/src /home/andrew/alfred/.venv/bin/python -m pytest …` (explicit venv python — bare `python` is not on PATH in a fresh agent shell and a `| tail` chain exits 0 anyway), prepend the fnm node path first (some python tests shell out to node). Note `pytest-randomly` is NOT installed — `-p no:randomly` is a no-op; drop it rather than carrying it as cargo (confirmed 2026-08-04). **Before trusting ANY worktree suite number, run the one guard on the axis that fails silent:** `PYTHONPATH=<tree>/src /home/andrew/alfred/.venv/bin/python -c "import alfred; print(alfred.__file__)"` and assert the path is inside your tree — a dead/typo'd PYTHONPATH is silently skipped and falls through to the main repo's editable install, producing plausible numbers about the wrong tree (live incident 2026-08-04; cwd/node/venv-python all fail loud, this is the only silent one).
